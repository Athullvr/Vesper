# Codex-compatible Vesper interface

This inventory is grounded in the existing terminal code and schemas generated locally from **codex-cli 0.162.1** on 2026-10-19. The terminal remains the frontend, Codex app-server remains the coding backend, and deterministic local handlers remain a separate execution path. See [RELIABILITY-AUDIT.md](RELIABILITY-AUDIT.md) for fixes, executed tests and runtime limits.

**Protocol scope**

Both ordinary and `--experimental` JSON schema bundles were inspected. The ordinary bundle contains 105 client request methods, 10 server request methods and 84 notification methods; the experimental bundle contains 170, 11 and 84 respectively. “Supported” below means present in that installed version's schema, not that every server-side capability was exercised, configured or authenticated. The app-server command itself remains experimental.

Vesper currently sends only `clientInfo` at initialization. It does **not** opt into `capabilities.experimentalApi`. Ordinary schemas already expose the main thread/turn methods, model/configuration reads, skills, MCP and many plugin methods. `plugin/search`, `turn/settings/update`, custom `dynamicTools` and some extended thread/permission fields are experimental. Their presence in the larger bundle is not permission to send them from the current client.

The offline smoke verified initialization, thread start, turn start and item events, interruption, and resumption in a second process. It did not verify a successful authenticated model answer, live approval operation, MCP connection or plugin installation.

**Minimal architecture and incremental migration**

Keep `routing-core.js` independent of presentation and side effects. Keep fixed local handlers separate from the app-server. Preserve `LocalResult` and `routeRequest` return shapes, existing session schema, and the CLI dependency-injection seams used by tests. Preserve the server as the authority for turn/operation completion and Codex configuration.

The current code has two result paths rather than a unified state store. This audit deliberately adds only a bridge: `progress` notifications retain `{ type: "codex_progress", method, params }` after connection/thread/turn filtering. It also fixes lifecycle and approval ownership. Raw payloads remain in memory; they are not added to session files or indiscriminately printed.

The next architecture can be introduced incrementally:

1. Add a small pure request-state reducer and an event adapter around the existing frontend. Suggested event kinds: request started, local result, agent delta, tool activity, approval requested/resolved, connection lost, and request finished. These names are a proposal, not a newly implemented API.
2. Give every displayed request a client execution ID independent of session UUID, Codex thread ID, turn ID and item ID. Local requests have no Codex IDs. Associate activity and approvals with all available IDs, never only the current screen or latest prompt.
3. Preserve ordered events and result provenance. Local confirmed/stale/unknown/unavailable is evidence status; Codex completed/failed/interrupted is execution status. Do not collapse them into a single success boolean.
4. Render bounded, escaped tool/diff/result views from that state. A display truncation must never conceal approval-relevant details while still offering an unrestricted yes. Approval choices are separate from app-server acknowledgements and operation outcomes.
5. Add history reads and session selection without changing existing UUID files. For forks, create new metadata. Decide explicitly whether and how to retain local-result history before changing privacy/storage behavior.
6. Add a version/capability adapter for model/config/ecosystem UI. Recheck generated schemas per installed version; unsupported methods must produce a clear unavailable feature, not guessed RPC parameters.
7. Migrate the VS Code transport to the tested shared client behind its existing UI callbacks. Preserve its read-only/decline-only policy via an explicit adapter. Do not copy terminal approval defaults into it implicitly.

Before any larger refactor, keep the current interface working and use the existing mock protocol tests as contract tests. Add reducer transition tests and only then migrate one event family or one frontend at a time.

**Priorities and remaining gaps**

- **P0 — reliability, safety, sessions, routing:** landed freshness and lifecycle fixes; preserve regressions and no-turn routing guarantees. Next, correlate full file changes with approval prompts, cancel stale pending approval UI on disconnect, and test server output ordering before start acknowledgement. Verify one authenticated end-to-end fallback and approval refusal when external access is approved. Harden or migrate the older extension transport before claiming equivalent reliability. Maintain the strict distinction between operation success, turn completion and local evidence.
- **P1 — usable interactive coding:** visible commands/tools/output/exit results, diffs, retry/progress state, structured user questions, history/session picker, multiline input, interrupt without exit, active model/policy visibility and final-message reconciliation. Keep this within the existing terminal.
- **P2 — supported configuration/ecosystem:** model/reasoning controls validated against catalog; configuration and managed-policy UI; skills, MCP status/elicitation, plugins/marketplaces, auth status and optional branching. Use ordinary methods first; experimental opt-in needs an explicit compatibility strategy.
- **P3 — Vesper extensions:** project memory and retrieval with evidence provenance; optional ML tools/workflows after the shared event/approval contracts are stable. No database or model choice is justified by the current deterministic routing results.

**Update (file-change approval milestone):** the in-memory per-turn file-change cache keyed by thread/turn/item ID is implemented in `file-change-approval.js`; the diff is shown before the v2 file approval prompt and the request is declined when evidence is missing, stale, malformed, oversized or invalidated during review. Legacy `applyPatchApproval` and `grantRoot` requests are declined. Not yet done: showing diffs outside approvals, `turn/diff/updated` aggregation, command-approval correlation with `commandExecution` items, and live-server verification.

The **next smallest, safest implementation step** is rendering bounded, escaped command-execution activity (`item/started`/`item/completed` commandExecution items: command, cwd, status, exit code) in the terminal, keyed by the same thread/turn/item identity, so command approvals and results become visible without changing routing, session metadata or security policy.
